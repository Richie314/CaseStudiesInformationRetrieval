# Memory budget and latency decomposition of in-memory graph ANN indexes — literature notes

Scope: (1) how much of an in-memory graph index is adjacency vs. vectors, especially once vectors are compressed; (2) vector compression schemes used *with* graphs and the per-vector byte budgets they reach; (3) where search time goes (distance computation vs. neighbor-list / vector fetches vs. bookkeeping), hops and distance computations per query; (4) benchmark datasets and memory limits. Numbers are quoted from the papers (PDF text extracted locally); derivations of my own are marked **[derived]**. Claims I could not verify are marked **[unverified]**.

---

## 1. Memory model of a graph index: formulas from the libraries/papers

* **HNSW paper** — Malkov & Yashunin, "Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs", IEEE TPAMI 2020 (arXiv:1603.09320, https://arxiv.org/abs/1603.09320). §4.2.3 "Memory cost": *"The memory consumption of the Hierarchical NSW is mostly defined by the storage of graph connections … the average memory consumption per element is (Mmax0 + mL·Mmax)·bytes_per_link … four-byte unsigned integers … typical close to optimal M values usually lie in a range between 6 and 48. This means that the typical memory requirements for the index (excluding the size of the data) are about 60–450 bytes per object."*
* **hnswlib** — ALGO_PARAMS.md (https://github.com/nmslib/hnswlib/blob/master/ALGO_PARAMS.md): *"M … also determines the algorithm's memory consumption, which is roughly M * 8-10 bytes per stored element"*; recommended M = 12–48. Source (`hnswlib/hnswalg.h`, https://github.com/nmslib/hnswlib/blob/master/hnswlib/hnswalg.h): `maxM0_ = M_ * 2; size_links_level0_ = maxM0_ * sizeof(tableint) + sizeof(linklistsizeint); size_data_per_element_ = size_links_level0_ + data_size_ + sizeof(labeltype);` with `tableint`/`linklistsizeint` = `unsigned int`, `labeltype` = `size_t`. So the level-0 block per element is **(2M·4 + 4) B of links + d·4 B of data + 8 B label**, plus `size_links_per_element_ = M·4+4` per upper level. `searchBaseLayerST` issues `_mm_prefetch` on the visited-array entry and on `data_level0_memory_ + id*size_data_per_element_ + offsetData_` of the *next* neighbor (one vector per neighbor, one level-0 block per hop).
* **Faiss** — wiki "Guidelines to choose an index" (https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index): *"The memory usage is (d * 4 + M * 2 * 4) bytes per vector"*, 4 ≤ M ≤ 64. Wiki "Faiss indexes" (https://github.com/facebookresearch/faiss/wiki/Faiss-indexes): IndexHNSWFlat "4*d + x*M*2*4" bytes/vector; *"IndexHNSW supports the following Flat indexes: IndexHNSWFlat (no encoding), IndexHNSWSQ (scalar quantizer), IndexHNSWPQ (product quantizer), IndexHNSW2Level (two-level encoding)."* Faiss paper (Douze et al., "The Faiss library", arXiv:2401.08281, https://arxiv.org/abs/2401.08281), graph section: *"Most graph methods fix the number of outgoing edges per node, which adjusts the trade-off between search speed and memory usage. The memory usage per vector breaks down into (1) the possibly compressed vector and (2) the outgoing edges for that vector"*; *"Increasing the number of edges improves the results until 64 edges, beyond which performance deteriorates."* Faiss issue #1747 (https://github.com/facebookresearch/faiss/issues/1747) attributes the hnswlib-vs-Faiss HNSW gap on ann-benchmarks to the missing `_mm_prefetch` of next-step vectors.
* **DiskANN / Vamana** — Subramanya, Devvrit, Kadekodi, Krishnaswamy, Simhadri, NeurIPS 2019 (https://proceedings.neurips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html). PQ *"short codes (e.g., 32 bytes per data point)"* in RAM; *"On the disk, for each point i, we store its full precision vector x_i followed by the identities of its ≤ R neighbors. If the degree of a node is smaller than R, we pad with zeros"* (fixed R·4 B adjacency per node, offset = id × record). *"just storing the vector data for a billion points in 100 dimensions would far exceed the RAM on a workstation!"* SIFT1B one-shot index: L=125, R=128, α=2, peak build memory ≈1100 GB, average degree 113.9; merged index: R=64 per shard, 348 GB on disk, avg degree 92.1. In-memory comparison on SIFT1M/GIST1M/DEEP1M used HNSW M=128, efC=512 and Vamana L=125, R=70, α=2. Serving: >5000 QPS, <3 ms mean latency, 95%+ 1-recall@1 on 16 cores / 64 GB.
* **Intel SVS / LVQ** — Aguerrebere, Bhati, Hildebrand, Tepper, Willke, "Similarity search in the blink of an eye with compressed indices", PVLDB 16(11) 2023 (https://www.vldb.org/pvldb/vol16/p3433-aguerrebere.pdf, arXiv:2304.04759, code https://github.com/intel/ScalableVectorSearch). LVQ-B footprint per vector = ⌈(d·B + 2·16)/8/32⌉·32 bytes, i.e. padded to half cache lines (Eq. 4). Figure 1 caption: *"For graph methods, the memory footprint is a function of the graph out-degree R and the vectors' footprint."*

### 1.1 Published memory breakdowns (graph vs. vectors)

**SVS Table 1** ("Memory requirements (graph + vectors) for graph building", GiB) for **deep-96-1B**:

| R | FP32 | LVQ-4 | ratio |
|---|---|---|---|
| 32 | 477 | 168 | 2.84 |
| 64 | 596 | 287 | 2.08 |
| 128 | 834 | 525 | 1.59 |

**[derived]** The totals decompose exactly as vectors + n·R·4 B: FP32 vectors = 1e9×384 B = 357.6 GiB; graph = 119.2 / 238.4 / 476.8 GiB for R = 32/64/128 (sum 476.8 / 596.0 / 834.4 ✓); LVQ-4 vectors ≈ 1e9×52 B = 48.4 GiB (sum 167.6 / 286.8 / 525.2 ✓). Hence with 4-bit vectors **the adjacency is 71% (R=32), 83% (R=64) and 91% (R=128) of index memory** — the paper does not say this in words, but its table implies it. The paper's low-memory production configuration, LVQ-8 + R=32 on deep-96-100M, has a *"memory footprint of 24GiB"* (**[derived]** 100M × (128 B padded LVQ-8 + 128 B adjacency) = 23.8 GiB → graph ≈ 50%); it beats Vamana/HNSWlib/FAISS-IVFPQfs/ScaNN by 2.3×/2.2×/20.7×/43.6× QPS at 0.9 10-recall@10 on deep-96-1B with 3.0×/3.3×/1.7×/1.8× less memory. SVS also reports that LVQ cuts *"total memory-footprint (considering the space occupied by the graph and the vectors) of up to 2.7x"* on 768-d data — the graph is what limits the ratio.

**SymphonyQG** — Gou, Gao, Xu, Long, "SymphonyQG: Towards Symphonious Integration of Quantization and Graph for ANN Search", SIGMOD 2025 (arXiv:2411.12229, https://arxiv.org/abs/2411.12229; DOI https://dl.acm.org/doi/10.1145/3709730). Explicit space model: *"SymphonyQG uses 32×D bits to store the raw vectors and 32×R bits (R integers) to store a vector's neighbors … creates quantization codes for all its R neighbors. Each quantization code takes D bits … total space cost of our index is n×(32D + 32R + DR) bits … Under the typical settings of the out-degree (R = 32 and 64), the overhead for storing the codes is 1x and 2x of that for storing the raw vectors."* **[derived]** per edge: 4 B id + D/8 B duplicated RaBitQ code (20 B/edge at D=128). Table 3 (GiB): SIFT1M SymphonyQG 1.5 vs OG-LVQ 0.5 vs Glass-NSG 0.7 vs HNSWlib 0.7 (raw data 0.5); GIST1M 12.5 / 1.7 / 3.8 / 4.2 (raw 3.6); Deep-100M 140.3 / 30.9 / 51.6 / 59.2 (raw 37.8). The degree is refined so every vertex has exactly a multiple of 32 out-edges (FastScan batch). Speed: *"at 95% recall, SymphonyQG achieves 1.5x-4.5x QPS compared with the most competitive baselines and 3.5x-17x QPS compared with … HNSWlib."* It prefetches the block of the best candidate when updating the beam.

**Link & Code** — Douze, Sablayrolles, Jégou, CVPR 2018 (arXiv:1804.09996, https://arxiv.org/abs/1804.09996). Fixed budget of 64–128 B/vector *including* links: notation L6&OPQ40 = 6 links × 4 B = 24 B + 40 B OPQ code; *"there is a clear trade-off enforced by the memory constraint. The search is ineffective with too few links … the accuracy is also impacted by a too strong approximation of the vector"* (Fig. 5, Deep1M, all setups at 64 B). Fig. 3 note: *"The HNSW memory size is larger because of the graph connectivity."* This is the earliest explicit link-bytes-vs-code-bytes budget.

**Severo, Ottaviano, Muckley, Ullrich, Douze (Meta), "Lossless Compression of Vector IDs for Approximate Nearest Neighbor Search"**, arXiv:2501.10479 (Jan 2025, https://arxiv.org/abs/2501.10479). The most explicit statement found: *"for inverted file and graph-based indices, auxiliary data such as vector ids and links (edges) can represent most of the storage cost."* and *"For graph based methods, each outgoing edge is defined by the id of the target node. Depending on the type of index, these ids can represent a significant fraction of the storage."* Results (bits per edge; uncompressed 32, "compact" ⌈log N⌉ = 20 for 1M): NSG16…NSG256 on SIFT1M/Deep1M/FB-ssnpp: Elias–Fano 15.7–18.1, ROC 16.2–20.9; Random Edge Coding 13.6–17.6; HNSW32 base layer 13.6–15.9 bits/edge (*"For HNSW, we compress only the base level graph since other levels occupy negligible storage"*); *"best compression rate being to 50% of the original size for NSG256"*. Search cost (Table 2, s per 10k queries, SIFT1M): NSG16 uncompressed 0.12 → EF 0.14 → ROC 0.29; NSG256 0.27 → 0.32 → 0.54; on FB-ssnpp NSG256 2.8 → 2.8 → 4.1. So EF costs ≤ ~20% while entropy coding (ANS/Fenwick) costs ~2×. **No table splitting graph bytes vs vector bytes is given.**

**Lantern blog** (industry, non-peer-reviewed; https://lantern.dev/blog/calculator): for 128-d vectors *"neighbor lists take up about half of the index memory footprint"*, and as quantization shrank vectors *"neighbor lists … became the dominant component"*. Consistent with the arithmetic above but not citable as a result.

**LEANN** — Wang et al. (Berkeley), "LEANN: A Low-Storage Vector Index", arXiv:2506.08276 (https://arxiv.org/abs/2506.08276): drops the embeddings entirely (recomputes them at query time), keeps a pruned graph, index ≤5% of raw data / up to 50× smaller — the limiting case where the graph *is* the index; cites Severo et al. for the graph's storage share.

**Other layouts.** NDSearch (Wang et al., arXiv:2312.03141, https://arxiv.org/abs/2312.03141; near-data-processing accelerator) repeats *"in HNSW, the memory consumption per vertex ranges from 60 bytes to 450 bytes"* and states *"all these ANNS workloads are memory-bound"*. COMPASS/DecoupleVS (arXiv:2604.09173, https://arxiv.org/abs/2604.09173) separates neighbor lists from vectors on disk so each can be compressed by its own scheme (up to 58.7% storage reduction) — disk-resident, but the same "two components, two compressibilities" argument.

**[derived] Rule of thumb for 1M–100M in-memory indexes.** hnswlib, M=16 (32 level-0 links = 132 B incl. count) or Vamana/SVS R=32 (128 B): float32 d=128 → graph ≈ 20% of 652 B/node; d=96 LVQ-8 (128 B) → 50%; PQ32/2-bit RaBitQ (32 B) → 80%; 1-bit RaBitQ at d=128 (16 B + ~8 B of factors) → ~85%. Upper HNSW layers add O(M·4/ (M−1)) B on average, negligible.

## 3. Where search time goes

* **SVS (VLDB'23)**: *"In graph search, most of the search time is spent (1) performing random memory accesses to retrieve the vectors associated with the out-neighbors of each node and (2) computing the similarity between the query and each vector."* *"The inability to effectively prefetch vectors with a hardware prefetcher means that the latency of accessing random vectors cannot be easily hidden … the simplicity of the distance computation kernel and the aforementioned fetching issues ultimately make the workload memory-bandwidth limited."* Their optimized search reaches 90% (float16) and 78% (LVQ-8) of the socket's 174 GB/s read bandwidth; software prefetch with tuned prefetch-offset / prefetch-step=2 gives up to 2× over no-prefetch, while the naive "prefetch the next vector" (step=1) gives no gain; a better visited set gives 15–20%. LeanVec/GleanVec restate: *"graph search is bottlenecked by the memory latency of the system, as we are fetching database vectors from memory in a random-like access pattern."*
* **ADSampling** — Gao & Long, SIGMOD 2023 (arXiv:2303.09855, https://arxiv.org/abs/2303.09855): *"on datasets with various dimensions from 256 to 960, DCOs [distance comparison operations] take from 77.2% to 87.6% of the total running time of HNSW"* (95% recall, K=100; hardware optimizations disabled). Note this attributes vector *fetch + arithmetic* to "DCO".
* **FINGER** — Chen et al., WWW 2023 (arXiv:2206.11408, https://arxiv.org/abs/2206.11408): *"starting from the mid-phase of a search, over 80% of distance calculations are larger"* than the current k-th best, i.e. do not change the result; approximating them gives 20–60% speedup over HNSW.
* **Graph reordering** — Coleman, Segarra, Smola, Shrivastava, NeurIPS 2022 (arXiv:2104.03221, https://arxiv.org/abs/2104.03221). Table 1 (perf, SIFT100M, misses / data loads): original L1 19.53%, L2 13.9%, L3 6.5%, TLB 3.85%; Gorder 14.46 / 9.6 / 4.0 / 2.14; Table 2 (cachegrind, node traversals + distance computations): L1 22.76% → 19.28%, L3 13.56% → 8.32%. P99 latency on SIFT100M −17% (RCM) / −30% (Gorder); query time improves *"up to 40%"* on large datasets. Nodes are flat records (vector 128 B SIFT / 384 B DEEP / 3.8 kB GIST + link array), so *one node spans several cache lines*. **[unverified]** The often-repeated "≈40% of query time is memory access" is not in the paper text; the 40% is the speedup.
* **Speed-ANN** — Peng, Zhang, Li, Jin, Ren, arXiv:2201.13007 (https://arxiv.org/abs/2201.13007) and **iQAN**, PPoPP 2023 (https://doi.org/10.1145/3572848.3577527): best-first search needs *"> 400 search steps … to find the 100-nn with 0.999 recall"* on SIFT1M; single-query search draws only 1.0–3.3 GB/s (SIFT1M 1.9, GIST1M 3.3, SIFT100M 1.0) and even edge-wise parallelism with 64 threads uses *"less than 5% of the peak hardware memory bandwidth (~80 GB/s)"*; laying out neighbor vectors contiguously ("neighbor grouping") gives up to 1.22×; iQAN reaches up to 37.7×/76.6× lower latency via path-wise intra-query parallelism.
* **AverSearch** — Luo et al. (Tsinghua), arXiv:2504.20461 (https://arxiv.org/abs/2504.20461): fork-join intra-query parallel search achieves only 108 GB/s of 266 GB/s (<40%); a micro-benchmark *"mimicking the expansion of a vertex with 32 out-edges"* reaches 36.19% of theoretical bandwidth; the fix is a fully asynchronous pipeline of vertex expansions. Confirms the per-hop unit of work = 1 adjacency fetch + ~32 vector fetches.
* **ParlayANN** — Manohar, Shen, Blelloch, Dhulipala, Gu, Sun, Simhadri, PPoPP 2024 (arXiv:2305.04359, https://arxiv.org/abs/2305.04359; https://github.com/cmuparlay/ParlayANN): Vamana/DiskANN, HNSW, HCNNG, pyNNDescent at 1B scale on 128 vCPU / 1–2 TB; *"the edge-list for each vertex is kept at a fixed length so we can calculate its offset from the vertex id"*; an approximate visited hash table sized beam² *"small enough to fit the table in the first-level cache"* improves all algorithms by 28.6–44.5% — bookkeeping matters at this scale. Fig. 3 plots *distance comparisons vs recall* on the billion-scale sets.
* **Hops / distance computations per query.** Wang, Xu, Yue, Wang, "A Comprehensive Survey and Experimental Comparison of Graph-Based ANNS", PVLDB 14(11) 2021 (arXiv:2101.12631, https://arxiv.org/abs/2101.12631; SIMD/prefetch disabled, single thread, parameter tables labelled Recall@10 = 0.99). Table 4 average out-degree (SIFT1M / GIST1M): HNSW 49 / 57, NSG 24 / 13, Vamana 50 / 50, HCNNG 61 / 42, DPG 76 / 94. Table 5 candidate-set size CS and query path length PL (= hops): SIFT1M HNSW CS 66, PL 47; NSG 101 / 85; HCNNG 97 / 37; NSSG 255 / 157; GIST1M HNSW 181 / 130, NSG 867 / 826; GloVe-100 HNSW 505 / 334. **[derived]** distance computations ≈ hops × (out-degree − revisits) → ~2,000 for HNSW on SIFT1M, ~7,000 on GIST1M at recall 0.99. The survey concludes *"the search efficiency of graph-based ANNS algorithms mainly depends on the number of distance evaluations during the search."* DiskANN reports Vamana needs *"2–3 times fewer hops for search to converge on large datasets compared to HNSW and NSG"* at 5-recall@5 = 98% with beam width 4.
* **Disk-side pipelining (for contrast).** PipeANN — Guo & Lu, OSDI 2025 (https://www.usenix.org/conference/osdi25/presentation/guo; ACM TOS https://dl.acm.org/doi/10.1145/3793926; https://github.com/thustorage/PipeANN): overlaps I/O of successive hops, 1.14–2.02× the latency of in-memory Vamana, 35% of DiskANN's.

## 5. Motivation summary (for the paper's introduction)

1. **Graph memory is fixed per node, vector memory is not.** Every mainstream library stores adjacency as a fixed-length array of 32-bit ids: 2M·4 B at HNSW level 0 (hnswlib source; Faiss "(d·4 + M·2·4) bytes per vector"), R·4 B per Vamana/SVS node (DiskANN §3.2; SVS Table 1). Malkov & Yashunin already put this at 60–450 B/object "excluding the size of the data". Faiss's own description is that per-vector memory "breaks down into (1) the possibly compressed vector and (2) the outgoing edges".
2. **Vector compression has shrunk the other term by 4–30×.** PQ32 in DiskANN, LVQ-4/8 in SVS, LeanVec (9.6×), RaBitQ (1 bit/dim, 16 B at d=128, now in Lucene's HNSW), NGT-QG/SymphonyQG (codes co-located with the adjacency). At 32–64 B per vector the 128 B adjacency of an R=32 graph is 67–80% of the index, and SVS's Table 1 implies 71–91% of a 168–525 GiB deep-96-1B index is adjacency once vectors are LVQ-4 (**[derived]**). The Meta compression paper says it in words: *"auxiliary data such as vector ids and links (edges) can represent most of the storage cost"* (Severo et al. 2025), and Link & Code (2018) already had to trade link bytes against code bytes inside a 64 B budget.
3. **The access pattern is one adjacency fetch per hop followed by one vector fetch per neighbor, and it is latency/bandwidth-bound.** SVS: "most of the search time is spent (1) performing random memory accesses to retrieve the vectors associated with the out-neighbors of each node and (2) computing the similarity"; ADSampling: 77–88% of HNSW time in distance-comparison operations; Coleman et al.: ~20% L1 and 6–14% L3 miss rates on SIFT100M, up to 40% faster with a cache-aware node order; Speed-ANN/AverSearch: single-query search uses 1–3 GB/s of ≥80 GB/s, expansion of a 32-out-edge vertex reaches 36% of bandwidth. Hops at recall 0.99 are ~50 (SIFT1M) to ~130–330 (GIST1M, GloVe) with 24–60 neighbors examined per hop (Wang et al. 2021), >400 steps for 100-NN at 0.999 (Speed-ANN). Prefetching the *next* vector and tuning the visited set are worth 1.2–2× (SVS, ParlayANN), which is exactly the budget a decoder for a compressed adjacency must not eat.
4. **Existing adjacency compression costs latency.** Severo et al. get NSG/HNSW edges from 32 to ~14–18 bits (≈2×) but Elias–Fano adds ~15–20% and ANS ~2× to search time; LEANN's alternative (throw away the vectors, recompute) shifts cost to a GPU. SymphonyQG/NGT-QG go the other way and *inflate* the per-edge cost to 20 B by duplicating codes for locality. Nobody has shown a compressed adjacency with cache-line-aware decoding that is *free* at search time.

**What a paper making this claim must report:** (a) bits/edge (and B/node incl. offsets) vs. the 32-bit baseline, on graphs of R = 16–64 for SIFT1M, GIST1M, GloVe-100, DEEP-10M, ideally also 100M; (b) total index bytes split into vectors / adjacency / offsets / cache, for float32, SQ8, PQ32, LVQ-4/8 and RaBitQ vectors; (c) QPS (single-thread and multi-thread) at fixed recall@10 ∈ {0.90, 0.95, 0.99} against hnswlib, Faiss HNSW, SVS/Vamana and SymphonyQG, on the same graph so only the adjacency representation differs; (d) per-query counters: hops, distance computations, adjacency bytes touched, LLC misses per hop (perf), decode ns per neighbor list, cache hit rate of the neighbor-list cache; (e) bandwidth consumed per query at saturation (GB/s), since the current best implementations are bandwidth-bound; (f) build-time overhead of the encoder and the cost of updates if any.
